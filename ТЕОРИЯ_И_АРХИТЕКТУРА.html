Лабораторные работы №2 и №3 • Система управления сотрудниками и расписанием

1. Зачем микросервисы вместо монолита?

В первой лабораторной работе система была монолитом: одно Spring Boot приложение, единый процесс JVM, одна общая база данных.

  • Проблема монолита: если падал модуль учета смен, падала вся система. Нельзя было масштабировать модуль явок отдельно от тяжелого модуля кадров.
  • Решение в ЛР2: разбили на автономные микросервисы. Если падает employee-service, сервис расписаний schedule-service продолжает работать за счет Fallback-заглушки (Circuit Breaker)!

4. Реактивный стек vs Классический (WebFlux vs MVC)

1. КЛАССИЧЕСКИЙ БЛОКИРУЮЩИЙ СТЕК (Employee & Schedule Services - Spring MVC + JPA):
   
   Клиент ──► [HTTP Запрос] ──► Поток #1 (Thread)
                                       │
                                       ▼  Блокирующий вызов JDBC
                                 [Поток ждет ответ БД и спит]
                                       │
   Клиент ◄── [HTTP Ответ]  ◄──────────┘

   * Модель: Thread-per-request (1 поток ОС на 1 запрос).
   * Минус: При медленной БД тысячи потоков просто спят, забивая память.


2. РЕАКТИВНЫЙ НЕБЛОКИРУЮЩИЙ СТЕК (Attendance Service - Spring WebFlux + R2DBC):

   Клиент 1 ──► [Запрос 1] ─┐
   Клиент 2 ──► [Запрос 2] ─┼──► [Event Loop: всего 2-4 потока на весь CPU]
   Клиент 3 ──► [Запрос 3] ─┘               │
                                            ▼  Неблокирующий вызов R2DBC
                                  [Поток НЕ ждет, а сразу берет след. задачу]
                                            │
                                            ▼  БД прислала данные (Callback)
   Клиент   ◄── [Stream / Chunked] ◄────────┘

   * Модель: Event Loop (событийно-ориентированная, как в Node.js / Nginx).
   * Плюс: Огромная пропускная способность при мизерном потреблении памяти.

Разница между Mono и Flux:

  • Mono<T> — вернет 0 или 1 элемент (асинхронный аналог Optional<T>). Пример: getById(id).
  • Flux<T> — вернет поток от 0 до N элементов (асинхронный стрим). Пример: /api/attendance/stream.

Зачем SliceResponse вместо Page:

Page делает тяжелый запрос SELECT COUNT(*), который тормозит на миллионах записей. SliceResponse запрашивает LIMIT 21 вместо 20. Если вернулась 21 запись — значит есть следующая страница (hasNext = true), и COUNT(*) не вызывается вообще!

5. Межсервисные вызовы и Circuit Breaker (Предохранитель)

Когда schedule-service проверяет сотрудника, он вызывает EmployeeClient (OpenFeign). Если employee-service упал, срабатывает Circuit Breaker:

               Штатный режим: запросы идут в удаленный сервис
          ┌────────────────────────────────────────────────────────┐
          │                                                        │
          │                   ┌────────────────┐                   │
          └─────────────────► │     CLOSED     │                   │
                              │  (Нормально)   │                   │
                              └───────┬────────┘                   │
                                      │                            │
                                      │ Превышен порог сбоев       │ Тестовые запросы
                                      │ (> 50% ошибок или таймаут) │ успешны
                                      ▼                            │
                              ┌────────────────┐                   │
                              │      OPEN      │                   │
                              │ (Авария / Цепь │                   │
                              │   разомкнута)  │                   │
                              └───────┬────────┘                   │
                                      │                            │
                                      │ Прошло время ожидания      │
                                      │ (wait-duration = 10s)      │
                                      ▼                            │
                              ┌────────────────┐                   │
                              │   HALF-OPEN    │ ──────────────────┘
                              │ (Пробные 3 вызова)
                              └───────┬────────┘
                                      │
                                      │ Хоть один пробный упал
                                      └──────────────────────────► (снова в OPEN)

Зачем нужен Fallback? Чтобы сервис расписаний не вернул пользователю ошибку 500, а отдал понятный резервный ответ: "Employee Service временно недоступен".

6. Топ-10 каверзных вопросов на защите

1. Зачем нам Eureka, если есть Docker Compose (где сервисы доступны по имени)?
Docker DNS статичен. Eureka — это динамический реестр уровня приложения: она отслеживает реальное здоровье JVM через heartbeats и поддерживает динамическое масштабирование (например, 3 реплики сервиса сотрудников).
2. Почему attendance-service реактивный, а остальные сервисы нет?
Отметки явок генерируют непрерывный высоконагруженный поток событий (например, с турникетов). Реактивный стек на Netty и R2DBC позволяет обрабатывать десятки тысяч запросов в секунду на 2-4 потоках процессора без блокировок.
3. Чем Mono отличается от Flux?
Оба — реактивные потоки Project Reactor: Mono возвращает 0 или 1 элемент, а Flux возвращает последовательность от 0 до бесконечного числа элементов.
4. Почему мы убрали @Repository из интерфейсов репозиториев?
Spring Data автоматически находит все интерфейсы, наследующие JpaRepository или R2dbcRepository, и регистрирует их бины. Аннотация @Repository на них избыточна.
5. Что делает Circuit Breaker в состоянии OPEN?
В состоянии OPEN реальный сетевой запрос в упавший сервис даже не отправляется. Срабатывает быстрый отказ (Fail-Fast), и клиент мгновенно получает ответ из Fallback-метода.
6. Зачем нужен SliceResponse вместо Page?
Чтобы избежать медленного запроса COUNT(*) к базе данных. Запрашивается LIMIT size + 1, что идеально для бесконечной ленты.
7. Что делает аннотация @Transactional?
Обеспечивает атомарность: группа операций с БД либо фиксируется целиком (COMMIT), либо откатывается (ROLLBACK) при возникновении RuntimeException.
8. Как API Gateway понимает, куда перенаправить запрос?
По маршрутам (routes) и предикатам. Запрос с префиксом /api/employees/** перенаправляется на lb://employee-service с балансировкой нагрузки через Eureka.
9. Что делает BCrypt (в ЛР3)?
Одностороннее хэширование паролей с добавлением случайной соли (salt). Даже если база утечет, пароли в открытом виде восстановить невозможно.
10. Как работает JWT-авторизация (в ЛР3)?
Клиент передает токен в заголовке Authorization: Bearer <token>. Фильтр JwtAuthenticationFilter проверяет криптографическую подпись и извлекает роли без дополнительных запросов в БД.
